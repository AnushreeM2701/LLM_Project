This chapter gives a clear overview of the dataset and experimental
process used in this study. It describes the evaluation dataset with
examples, explains how the 786 model responses were collected, reports on
data quality checks that found real bugs, and shows where to find the
full code and repository for reproducibility.

These twelve examples make the differences between categories and
difficulty tiers clear, not just by their labels. Within a category, the
Easy and Medium examples are typically directly computable from the
question as stated, while the Hard (AIME) examples require a longer
chain of intermediate reasoning before the final numeric answer can be
reached, illustrated here by the Algebra, Combinatorics, and Probability
Hard-tier examples, each of which needs several derived quantities
before the final step. The Algebra examples are single equations or
expressions to solve for one unknown or one value. The Number Theory
examples require reasoning about divisibility or base-representation
conditions across all positive integers, not just a fixed set of
candidates. The Probability examples need a probability calculation over
a combinatorial structure. The Combinatorics examples require
recognising a counting or game-theoretic structure, from a direct
counting formula at the Easy tier to a strategy-based argument at the
Hard tier. The Hard-tier questions, drawn from AIME, additionally
require the kind of open-ended multi-step derivation characteristic of
that source, compared with the more directly computable
Hendrycks-sourced examples at the Easy and Medium tiers.

\section{Experimental Pipeline}
\label{sec:pipeline}

The experimental pipeline gathers 786 responses in total. This comes from
running 131 questions with both Chain-of-Thought and Tree-of-Thought
methods across three models (131 $\times$ 2 $\times$ 3 = 786). Instead of
processing everything in one long, uninterruptible batch, the pipeline is
built to be resumable and uses checkpoints. This was important because
free-tier API quotas were reached several times during data collection.

Each experiment is identified by its Question ID, model, and prompt type.
Before starting, the pipeline checks which experiment combinations are
already in the results file and skips those that are done. This means
the same script can simply be re-run to continue from wherever it
previously stopped, without manual tracking or restarting from scratch.
Each result is saved to the results file as soon as it finishes, one row
at a time. If the run is interrupted by an error, quota limit, or if the
process is stopped, all completed work is preserved.

This approach was important because the three providers have very
different free-tier rate limits. Mistral is limited to 2 requests per
minute, so it is much slower than Gemini or Groq. For example, Mistral
takes about 5 to 6 hours for a full dataset pass, while the other two
take only tens of minutes. To avoid wasting time, all three models run at
the same time, each in its own thread. This means the total run time
depends only on the slowest model. If a model's daily quota runs out
during a run, its thread stops without affecting the others or losing
any collected data. The run can be repeated later when the quota resets,
and only the unfinished combinations are processed.

Each result row also includes provenance information in addition to the
raw response. This includes the exact model version returned by the
provider's API (which may differ from the configured model alias, as
explained in Chapter~\ref{chap:methodology}), the specific prompt version
used, and the start time, end time, and execution time for each call.

\section{Data Quality Assurance}
\label{sec:data-quality}

To ensure the automated pipeline works correctly, a clear rule is
enforced: Answer Correct and Error Type must always agree. If a response
is marked incorrect but labelled with the error type ``Correct'' (or the
other way around), it signals a bug, not a real reasoning issue. This
rule is enforced in the code with \texttt{assert\_no\_stale\_error\_labels},
instead of just being assumed to hold. Checking results against this
rule during error classification helped surface two real answer-extraction
bugs that would have otherwise gone unnoticed and produced wrong data.

The first bug was related to LaTeX fraction notation. The extraction
logic could handle the basic \texttt{\textbackslash frac\{a\}\{b\}}
macro, but not the \texttt{\textbackslash dfrac} (display-style) or
\texttt{\textbackslash tfrac} (text-style) versions. If a model's
response used \texttt{\textbackslash dfrac\{3\}\{16\}} as the final
answer, the macro stayed in the text, and the fallback numeric extraction
picked up just the digit ``3'' instead of the correct value ``3/16''.
This meant a correct answer was marked as incorrect because of a parsing
error. This issue was found in real results data
(\texttt{PROB\_E\_003\_groq\_tot}) and fixed by updating the logic to
recognise \texttt{\textbackslash dfrac} and \texttt{\textbackslash tfrac}
as well.

The second bug was about embedded ordinal numbers. The extraction logic
searched for numbers in the response, but in a sentence like ``The 158th
marble is \textbf{gray},'' the number 158 is just an ordinal reference,
not the answer. The real answer, ``gray,'' is a word. Because the logic
matched ``158'' before checking for words, the pipeline recorded ``158''
as the answer instead of ``gray.'' This was found in real results data
(\texttt{NT\_E\_009\_groq\_cot}) and fixed by ensuring the logic does not
treat numbers with ordinal suffixes (like ``158th'') as standalone
numeric answers.

Regression tests (\texttt{tests/test\_response\_parser.py}) were added
for both fixes, using the exact failing inputs described above. This
way, if future changes to the extraction logic bring back either bug,
the tests will catch them automatically instead of letting them slip by.
